# V0.15.0 — Installation & Workspace Architecture

V0.15.0 separates the OrchestraX toolkit/runtime from the workspace it orchestrates.

## Goals

- OrchestraX installation no longer needs to be inside the workspace.
- Workspace becomes optional.
- Standalone projects are supported.
- Workspace scope is explicit.
- Workspace and project pack installations are supported.
- Existing instruction, agent, skill, Syntra, task, handoff, and provider systems continue to resolve against the independent OrchestraX installation.
- Copilot AI command projection remains intact.

## Workspace layout

A workspace initialized with `neo workspace init` contains:

```text
workspace/
├── projects/
├── documentation/
├── context/
│   └── syntra/
└── .orchestrax/
    ├── workspace.json
    └── packs/
```

The OrchestraX installation can live elsewhere.

## Standalone project layout

A project initialized with `neo project init` contains:

```text
project/
└── .orchestrax/
    ├── project.json
    ├── packs/
    └── syntra/
```

## Scope model

```text
OrchestraX installation
        |
        v
Workspace scope
        |
        v
Project scope
```

The installation supplies default capabilities. Workspace and project configuration provide selected/overridden capabilities.

## Pack commands

Workspace scope:

```text
neo pack install <pack> --workspace
neo pack installed --workspace
neo pack remove <pack> --workspace
```

Project scope:

```text
neo pack install <pack> <project>
neo pack installed <project>
neo pack remove <pack> <project>
```

When resolving a project, available pack sources include the OrchestraX installation, workspace-installed packs, and project-installed packs.

## Provider strategy

V0.15 does not attempt to make every AI client expose OrchestraX slash commands identically.

The provider-neutral core remains authoritative. Provider integrations are optional UX adapters.

The Copilot provider projection from V0.14.7 remains supported because it already provides useful `/...` command discovery in VS Code.

The CLI remains the universal control surface.

## Architectural rule

Do not place the OrchestraX installation inside every workspace merely to make the toolkit discoverable. Workspace state references the installed toolkit through the CLI/runtime, while workspace and project directories contain only their own configuration, selected packs, project state, documentation, and context.
